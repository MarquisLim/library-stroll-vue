## 3. Причины расхождения

**Установлено по данным.** У ID 1–20 последний успех был 24 октября, между 18:15:35 и 18:52:40 UTC. После каждого из этих успехов первый сбой пришёлся на 1 ноября, 21:00:00–21:00:01 UTC. Всего после последних успехов у этих работ 105 ошибок 502 с признаком сбоя соединения. Стадия последнего сбоя — `analysis` у 15 из 20, у пяти она неизвестна. У ID 21 все шесть ошибок отмечены на `analysis`, успешных попыток, точки и предыдущего `indexed_at` нет. Из 116 сбоев всех 21 работ 111 имеют признак сбоя соединения и пять — таймаута. Пять таймаутов относятся к более ранним попыткам.

**Наиболее вероятный сценарий.** Плановый reconcile повторно взял двадцать уже индексированных работ, поскольку им было больше 24 часов. Первые сбои сгруппированы в начале получасового слота, и в исторической ревизии `22ec98d` действовали тот же порог и расписание. Ошибка повторного анализа оставила прежние точки на месте, а метаданные пометила как `failed`. Источник dispatch не сохраняется в истории, а текущие контейнеры Scheduler, worker и AI API созданы после обеих волн ошибок. Их журналы за нужные окна пусты. Поэтому точный источник запуска первой волны и адрес неудавшегося соединения для попыток без стадии не установлены. Для последних попыток со стадией `analysis` сбой произошёл до шага `indexArtwork()`. Путь анализа в FastAPI обращается к Ollama.

**Порядок операций на момент аудита 4.1.2A.** `dispatch()` выставлял `pending`. Job ставил `processing`, увеличивал накопительный `attempts`, запускал анализ и сохранял его поля и `processed_at`. Затем FastAPI рассчитывал embedding и вызывал Qdrant upsert. После успешного ответа Laravel проверял ID и размерность, повторно читал работу, сохранял финальные поля `indexed` в MySQL и завершал запись попытки. Python возвращал размерность и ID без версии весов. SDK по умолчанию выполнял upsert с `wait=True`. [Новый порядок постановки](#12-безопасная-постановка-ai-заданий-412b-32b-1), [job](../../app/Jobs/AnalyzeAndIndexArtworkJob.php), [FastAPI index](../../ai-service/app/services/artwork_service.py#L73), [Qdrant upsert](../../ai-service/app/clients/qdrant.py#L89).

Есть несколько путей к состоянию «точка существует, SQL `failed`».

1. Ошибка повторного анализа, embedding или upsert оставляет предыдущую точку. Блок `catch` записывает новый статус и сообщение ошибки без очистки прежнего ID и хеша. Если анализ успел пройти, поля анализа и имя embedding-модели в MySQL могут измениться раньше точки.
2. После применения upsert могут потеряться HTTP-ответ или связь, либо не сохраниться метаданные, либо ответ может не пройти проверку. Если обработчик ошибки успеет обновить MySQL, результатом будет `failed` при уже записанной точке. Ошибка фиксации истории после обновления метаданных тоже попадает в общий `catch`. Если процесс оборвётся раньше, возможен зависший `processing`.
3. Laravel повторяет HTTP-запрос индексации до двух попыток при текущей конфигурации. Job может выполняться до трёх раз со своим backoff и начинать с анализа. Повтор с тем же ID перезаписывает точку, при отдельном HTTP-повторе пересчитывается embedding. Последний включённый в таблицу запуск перешёл в `failed` без подтверждённого нового upsert. Картина потерянного ответа Qdrant для этих данных не подтверждена. [HTTP-клиент](../../app/Services/AiService/HttpAiServiceClient.php#L72), [проверка ответа и фиксация](../../app/Jobs/AnalyzeAndIndexArtworkJob.php#L170), [catch и аварийное завершение](../../app/Jobs/AnalyzeAndIndexArtworkJob.php#L230).

## 4. Проверка `ai:reconcile`

| Механизм | Поведение и последствия |
|---|---|
| Возраст `indexed` | При `indexed_at < now() - 24 часа` запись попадает в первую группу вместе с `stale` и `processing`, у которого `updated_at` старше двух часов. `dispatch(force: true)` обходит проверку совпавшего хеша. Не проверяются существование точки, payload, версия embedding или доступность зависимостей |
| Повтор `failed` | Команда выбирает `attempts < 5`. Это накопительные запуски, включая успешные. У отдельного job до трёх попыток, поэтому один dispatch может перевести счётчик через порог до 6–7. Восстановление Ollama лимит не сбрасывает |
| Остальные ветки | Затем обрабатываются `pending` старше двух часов и опубликованные работы без метаданных. Для каждой пачки общий лимит, стабильного порядка нет. Команда увеличивает счётчик даже при пропуске, удалении метаданных или подавлении enqueue уникальной блокировкой |
| Scheduler после ручной смены статуса | Если 20 записей просто сделать `indexed` с прежним `indexed_at`, то все 20 станут кандидатами на ближайшем получасовом запуске при наличии места в пачке. Фиктивное обновление `indexed_at` отложит повтор до следующего истечения порога |
| Идемпотентность и дубли | Точки ID 1–20 имеют канонический UUIDv5, повтор с этим ID заменит существующую точку. Если сохранённый совместимый исторический ID утрачен, а старый ID отличается от UUIDv5, новый upsert может добавить вторую точку с тем же `artwork_id`. `ShouldBeUnique` по ID и хешу плюс `WithoutOverlapping` по ID ограничивают конкурирующие index jobs, но отдельный delete job эту блокировку не разделяет |
| Устаревшие и удалённые | Повторный upsert с тем же ID заменяет прежний payload. Успешное удаление работы при включённом AI ставит отдельный job, Qdrant удаляет по `artwork_id`. Код анализа пытается компенсировать upsert, если позже обнаружит удаление, снятие с публикации или запрет индексации. В `dispatchForMeta()` для исчезнувшей или снятой работы удаляется только строка метаданных. Устаревшую точку эта команда сама не проверяет и не удаляет |

За пределами автоматической сверки остаются недавний `indexed` с отсутствующей точкой, устаревший или непроверяемый payload, осиротевшая точка без SQL, неверный ID, конфликт нескольких точек, несовместимая модель той же размерности и пропущенные удаления. Поиск из Laravel дополнительно фильтрует SQL-видимость, что само по себе не синхронизирует Qdrant. [Условия reconcile](../../app/Console/Commands/AiReconcileCommand.php#L37), [расписание](../../routes/console.php#L11), [действие удаления](../../app/Actions/Artwork/DeleteArtwork.php#L14), [job удаления](../../app/Jobs/DeleteArtworkIndexJob.php#L40), [удаление Qdrant](../../ai-service/app/clients/qdrant.py#L110).

## 5. Риски восстановления

- Хеш канонизирует ревизию входных данных Laravel, включая UUID медиа и версии схемы/prompt. Он не является отпечатком вектора, весов, содержимого файла медиа или точного текста, который передавался embedding-модели. Для этих 20 точек имя из SQL, 1024 измерения и исторические сведения Ollama согласуются, но payload и журнал не связывают конкретный digest весов с каждой точкой. Активный тег может указывать на другие веса той же размерности. [Вычисление хеша](../../app/Services/AiService/ArtworkIndexingService.php#L11), [записываемый payload](../../ai-service/app/services/artwork_service.py#L73), [сведения об Ollama](ai-stage-04-01-ollama-recovery.md#8-совместимость-с-существующим-qdrant).
- Запись через рабочую коллекцию заменит существующую точку, если используется прежний ID, либо добавит дубль при ошибке сопоставления. Для группы B сохранение текущих 20 точек безопаснее до подтверждения происхождения или проверки нового индекса.
- Временная недоступность Qdrant не доказывает отсутствие точки. Переиндексацию по такому результату начинать нельзя. При конкурирующих изменениях контента или видимости решение, полученное в dry-run, может устареть до применения.
- Тестовый результат в отдельной коллекции не должен переводить метаданные активной коллекции в `indexed`. Переход на новую коллекцию требует отдельной проверки покрытия, режима чтения и плана отката.

## 6. Рекомендуемый алгоритм восстановления

1. Сначала выпустить изменение 4.1.2B, которое исключает повторный inference только из-за `indexed_at`. Пока действует прежнее расписание, статусы 20 старых точек оставить как есть. Снятие показателей и `--dry-run` допускаются при работающем Scheduler.
2. Сделать отдельную операцию с обязательным `artwork_id`. Пример интерфейса для реализации: `php artisan ai:reconcile-artwork 21 --dry-run`. Она считывает SQL, пересчитывает хеш, проверяет доступ через актуальные флаги работы и автора, ищет точку по ID и `artwork_id`, выводит группу и допустимое действие. В dry-run запрещены enqueue, запись статуса, inference, создание и изменение коллекций.
3. Для A предусмотреть явное применение к одной работе с повторной проверкой под общей блокировкой писателей. Сверить точку, её модель и digest, принадлежность к активной коллекции, ревизию и версию SQL-строки непосредственно перед условным обновлением. Если всё совпало, можно восстановить SQL-статус без повторного inference и сохранить подлинное `indexed_at`, счётчик и историю. В текущем снимке таких записей нет.
4. Для B оставить текущую точку и искать надёжное доказательство её происхождения. Если его нет, проверять новый embedding в **отдельной версионированной коллекции** на следующем этапе. Та же рекомендация для C при подтверждённом несовпадении хеша. Для D работу 21 выбрать первым кандидатом на одиночную индексацию в согласованной тестовой коллекции. Её исходный вектор не найден. Действия применяются к одной работе за раз, без смены модели и записи в текущий индекс. Для E или F сформировать отдельное решение, сохранив точки до проверки и подтверждения.
5. На повторном запуске одинаковая операция сверяет уже применённый результат и ничего не ставит в очередь второй раз. Для тестового upsert закрепить ID в пределах коллекции и проверять ответ и фактическое наличие точки после записи. При потерянном ответе сначала перечитать точку по ожидаемым идентификатору, хешу и fingerprint. При конфликте ревизии, смене доступа или неясном результате остановить применение, сохранить состояние журнала и повторить чтение.

## 7. Предлагаемые изменения в 4.1.2B

- Изменить выборку `AiReconcileCommand` и поведение Scheduler. Возраст можно использовать для планирования чтения индекса, а не как повод повторять inference. Сохранить ограниченный отбор реально зависших заданий. Различать просмотренные, подтверждённые, поставленные и пропущенные записи. Отдельно запланировать управляемый повтор после сбоя зависимости с бюджетом на текущую ревизию или инцидент. Накопительный `attempts` оставить для истории.
- Добавить проверку точки чтением без выдачи координат вектора. Различать найденную, отсутствующую, неоднозначную и недоступную точку. Для каждой операции фиксировать `artwork_id`, целевую коллекцию, ожидаемый ID, текущий хеш, версии схемы/prompt и результат проверки.
- Записывать модель и проверяемый digest именно той модели, которая вернула embedding, в payload и журнал успешной операции. Сохранить версию модели, размерность и имя коллекции рядом с привязкой SQL. Отделить результат последней попытки от подтверждения последней успешно записанной точки, чтобы не терять информацию о пригодном индексе при временной ошибке.
- Добавить single-artwork dry-run и явное применение. Общая блокировка на работу и условное обновление должны учитывать Scheduler, job индексации, job удаления и ручное исправление. Для незавершённого результата после отправки запроса повтор должен сначала сверять состояние Qdrant. Найденные дубли и осиротевшие точки вынести в список для подтверждённого точечного удаления.

## 8. Критерии проверки 4.1.2B

| Сценарий в изолированных тестах | Что должно произойти |
|---|---|
| `indexed` старше 24 часов, точка и fingerprint актуальны | Scheduler не запускает inference. Повторная проверка не меняет `indexed_at` |
| `indexed` недавний, но точка отсутствует | Диагностика видит D и предлагает действие для конкретной работы. Сбой Qdrant вместо ответа «нет точки» даёт F и запрещает запись |
| Хеш изменился, модель неизвестна либо имеет тот же размер и другой digest | C или B соответственно. Запрещено слепое восстановление статуса или запись в активный индекс |
| Два ID на одну работу либо несовпадение владельца точки | F, обе точки сохраняются до целевой проверки |
| A с доказанным fingerprint, повторное применение и гонка с изменением публикации | Одна условная запись SQL без inference, повтор — без изменений. Смена ревизии, снятие с публикации или `ai_indexing_enabled=false` до применения блокируют операцию |
| Успешный upsert, потерянный ответ или ошибка фиксации MySQL | Повтор находит ту же точку по ID и ревизии, не создаёт дубль. Неподтверждённый upsert не выставляет `indexed` |
| Таймауты или временный отказ зависимости при исчерпанных `attempts` | Автоматический повтор ограничен правилами восстановления. Разрешённый точечный повтор после восстановления сохраняет историю счётчиков |
| Удаление и upsert конкурируют | Общая блокировка и проверка текущей видимости исключают возврат удалённой точки. Ошибка удаления остаётся видимой для следующей сверки |
| Dry-run для каждой группы, Scheduler запущен, тестовая коллекция отделена | Нулевые записи в MySQL, Redis и Qdrant со стороны dry-run. Тестовая точка не меняет статус активной коллекции |

Для тестов использовать текущие `Http::fake` / `Queue::fake` в Laravel и Qdrant SDK в памяти. Первый живой шаг после изолированных тестов — оценить план для ID 21 в dry-run. Запись требует отдельно согласованного сценария. Реальные данные этого этапа не менялись. ## 9. Диагностическая команда 4.1.2B-2

Предыдущие разделы фиксируют аудит и предложения на тот момент. Для сверки одной работы после развёртывания обновлённых PHP и FastAPI доступны команды:

```powershell
php artisan ai:reconcile-artwork 1 --dry-run
.\scripts\docker.ps1 artisan ai:reconcile-artwork 21 --dry-run
```

Команда также работает без `--dry-run` и всегда обозначает режим `read-only`. Код завершения 0 означает, что выдана классификация A–E. F возвращает 1, недопустимый ID — 2. Вывод включает состояние MySQL и Qdrant, результаты сравнения хеша и версий, модель, известный fingerprint и рекомендацию. Рекомендация не запускает действие. [Команда Laravel](../../app/Console/Commands/AiReconcileArtworkCommand.php).

FastAPI обслуживает `GET /api/v1/artworks/{artwork_id}/index/inspect` только с настроенным и совпадающим `X-AI-Service-Key`. Дополнительный параметр `point_id` принимает сохранённый UUID. Сверка работает с целевой коллекцией из конфигурации. Она читает максимум две записи по `artwork_id` с `with_vectors=False`, включая приватные и заблокированные точки. При необходимости выполняет точечное чтение сохранённого ID и проверяет наличие неназванного вектора по фильтру без получения его координат. Ответ ограничен полями диагностики. Отсутствующие модель, digest и fingerprint передаются как `null`. Отсутствие коллекции и ошибка доступа к Qdrant дают HTTP 503 с различимыми кодами. [Маршрут FastAPI](../../ai-service/app/api/routes.py), [чтение Qdrant](../../ai-service/app/clients/qdrant.py).

### Приоритет классификации

1. Несуществующая публикация — E без вызова Qdrant. Для существующей публикации подтверждённый дубль или конфликт сохранённого ID даёт F, в том числе для скрытой работы. Если такого конфликта нет, скрытая, заблокированная, неопубликованная или исключённая из индексации работа получает E. Учитывается блокировка автора.
2. Для допустимой публикации ошибка доступа или некорректный ответ дают F. D присваивается, если коллекция успешно прочитана, точек работы нет и сохранённый ID, если был указан, также отсутствует. Точка без подтверждённого вектора или с несовпадающим ID при наличии локальной привязки даёт F.
3. Для сопоставленной точки подтверждённое расхождение Qdrant-хеша с текущей или сохранённой ревизией даёт C. Неизвестный хеш, отличающиеся версии схемы/prompt, флаги видимости или известная несовпадающая размерность дают F.
4. Для актуальной точки совпадения имени модели и размерности недостаточно. A требует совпадения имени и полного SHA-256 (`embedding_model_digest` или `embedding_fingerprint`) с последней успешной записью `analyze_and_index` в MySQL, привязанной к этой же коллекции, точке и хешу. Противоречивые сведения дают F. При отсутствии подтверждения — B. Команда не присваивает исторической точке digest установленной сегодня модели. [Сервис сверки](../../app/Services/AiService/ArtworkIndexInspectionService.php).

### Конкурентные операции

Для предварительной проверки A команда кратковременно берёт тот же ключ Laravel Cache, который использует middleware `AnalyzeAndIndexArtworkJob` для этой работы. Занятый ключ даёт отказ. Снимок учитывает текущий хеш, AI-метаданные, последнюю успешную попытку, ID и коллекцию точки, размерность и fingerprint. Допуск к индексации проверяется повторно по видимости, блокировке автора и `ai_indexing_enabled`. FastAPI также принимает прямые запросы индексации и удаления вне блокировки Laravel. Точка может измениться после второго GET, а SQL — после последнего чтения. | Backoff исключений | У индексации сохранены `[15, 60, 120]`, у удаления `[10, 30, 60]`. Laravel выбирает задержку по номеру резервации, поэтому после ожидания может выбрать последнее значение |

## 12. Безопасная постановка AI-заданий 4.1.2B-3.2B-1

- После внешнего SQL commit сервис заново читает работу, проверяет публикацию и `ai_indexing_enabled`, рассчитывает текущий `content_hash` и читает AI-метаданные. Rollback отменяет заявку до захвата уникального ключа. Возвращённый `true` внутри транзакции означает регистрацию заявки на момент commit. Вне транзакции он означает, что драйвер очереди принял задание. Синхронная очередь и драйвер `null` для этой постановки возвращают пропуск.
- Перед отправкой используется штатный ключ Laravel `ShouldBeUnique` по ID работы и хешу ревизии с TTL 900 секунд. Один из одновременных вызовов с этим ключом отправляет задание, остальные получают `false`. Ошибка отправки возвращается вызывающему коду, а захваченный ключ освобождается для повтора. При успешной отправке worker освобождает ключ по токену владельца. Ручной запрос из админки при пропуске получает HTTP 409. [Постановка](../../app/Services/AiService/ArtworkIndexingService.php), [ручная постановка](../../app/Http/Controllers/Admin/ArtworkController.php).
- Постановка сохраняет существующие AI-метаданные и не создаёт `pending`. Предыдущий статус, включая `indexed` для старой ревизии, виден до старта следующего задания. Worker под общей блокировкой работы в короткой SQL-транзакции перечитывает ревизию и метаданные перед записью `processing` и увеличением `attempts`. Автоматический job пропускает уже индексированную актуальную ревизию. Устаревший job может поставить свежую ревизию, пока удерживает блокировку выполнения. Постановка берёт только отдельный ключ уникальности ревизии. [Индексирующее задание](../../app/Jobs/AnalyzeAndIndexArtworkJob.php).
- `ai:reconcile` сверяет состояние кандидата с прочитанным снимком SQL. Для опубликованных работ он ставит `stale`, зависший `processing`, старый `pending`, `failed` с доступными попытками и работы без метаданных. Метаданные неопубликованных работ сохраняются. При изменившемся снимке или занятом ключе постановки кандидат учитывается как `skipped`. Ошибка драйвера попадает в отдельный счётчик и даёт ненулевой код возврата. Scheduler сохраняет интервал 30 минут и лимит менее пяти попыток для `failed`. Возраст `indexed` по-прежнему не участвует в отборе. [Команда сверки](../../app/Console/Commands/AiReconcileCommand.php).

Из 295 PHP-тестов в изолированном прогоне прошли 287, пропущены 8, выполнено 1449 утверждений. Отдельно исключён сценарий с `ai:reindex-all`. Регрессии проверяют commit и rollback, подавление дубля, ошибку очереди, конкуренцию с индексацией и предварительной проверкой, смену и возврат ревизии, два такта Scheduler и сохранение 21 фикстуры с исчерпанными попытками. [Тесты постановки](../../tests/Feature/ArtworkIndexDispatchTest.php), [тесты индексации](../../tests/Feature/ArtworkIndexingTest.php), [тесты сверки](../../tests/Feature/ArtworkIndexInspectionTest.php).

В сценарии использовалась SQLite в памяти, HTTP-вызовов не было. Рабочие данные и записи ID 1–21 в проверке не участвовали.

Worker вызывает AI API между короткими SQL-транзакциями, однако прежний middleware держит общий Redis-ключ весь `handle()`, включая inference. Сужение этой блокировки требует отдельной защиты от применения устаревшей попытки. Индексатор проверяет доступность и хеш перед отправкой в Qdrant и перед записью `indexed`. [Индексация](../../app/Jobs/AnalyzeAndIndexArtworkJob.php), [очистка](../../app/Jobs/DeleteArtworkIndexJob.php).

Этот режим проверяет соответствие ID и снова проверяет доступность работы на worker. Автоматической доставки накопившихся заявок пока нет. [Проверка Laravel](../../tests/Feature/AiArtworkVisibilityTest.php), [тесты FastAPI](../../ai-service/tests/test_search_visibility.py).

Запоздалый upsert после таймаута всё ещё может вернуть старый payload в Qdrant. Пока SQL запрещает доступ, такая точка отсеивается в поиске. Если работа вновь публична, проверка видимости сама по себе не подтверждает актуальность ревизии вектора. Qdrant также может пропустить разрешённую работу из-за устаревшего ограничительного флага. Изменение прав после последнего SQL-чтения и до ответа остаётся возможным. Следующий подэтап должен защитить записи и удаления по ревизии.
