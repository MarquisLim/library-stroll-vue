## Инструмент и входные данные

Инструмент состоит из [PowerShell-обёртки](../../scripts/research/vision-recovery.ps1), [проверки Laravel](../../scripts/research/vision-recovery-inspect.php) и [проверки моделей](../../scripts/research/vision-recovery-health.py). Он отправляет задания существующей командой `ai:index-artwork` и исполняет каждое через `queue:work --once`. Пайплайн `AnalyzeAndIndexArtworkJob`, поиск и RAG сохранены в прежнем виде.

JSON-манифест содержит имя Compose-проекта, имя коллекции, фиксированный массив `artwork_ids` и массив `approved_demo_ids`. Последний является явным списком работ, для которых можно включить индексацию. До изменения флага инструмент повторно проверяет, что работа демонстрационная, публичная, не заблокирована, принадлежит незаблокированному автору, является изображением и имеет оригинал и миниатюру. Для пользовательских работ с выключенной AI-индексацией разрешение не включается. Перечни проверяются на корректность и дубли. Хеш манифеста, имя проекта и размер пакета фиксируются в каталоге результатов.

Пилотный список из разных категорий — `38, 27, 32, 59, 61, 53, 39, 42, 22, 35`. Он зафиксирован до обработки. [Манифест пилота](../../storage/app/ai-stage-05-04/5.4-0c2/pilot-manifest.json)

Перед каждым заданием проверяются `/ready`, конфигурация Vision 45 с и 3072 токена, `think=false` и дайджесты моделей `qwen3:8b`, `qwen3-vl:4b-instruct` и `qwen3-embedding:0.6b`. Дайджесты зафиксированы в инструменте по результатам 5.4-0B1. Проверка Laravel требует Redis-очередь `ai` и отключённые reranking и ColBERT. Существующие миниатюры используются штатным job. Если оригинал или миниатюра отсутствует, работа пропускается. Запущенные сервисы `worker-ai` и `scheduler` в выбранном Compose-проекте останавливают запуск инструмента, чтобы одной очередью управлял один worker.

## Запуск и продолжение

Выполнять команды из корня репозитория в PowerShell 7. Сначала подготовить манифест с фактическим проектом, коллекцией и утверждёнными ID. Проверить план без изменения каталога.

```powershell
.\scripts\research\vision-recovery.ps1 -Project library-stroll-54-pilot `
    -Manifest storage/app/ai-stage-05-04/5.4-0c2/pilot-manifest.json `
    -OutputDir storage/app/ai-stage-05-04/5.4-0c2/run -BatchSize 5 -DryRun
```

Для выполнения использовать ту же команду без `-DryRun`. Один вызов обрабатывает не более `BatchSize` работ. Повторный вызов продолжает тот же список, проверяет журнал и пропускает записи, у которых подтверждены актуальная ревизия, UUID медиа, последний успешный Vision-run и соответствующая точка Qdrant. Для каждого задания фиксируются намерение отправки, статус, время, источник анализа, предупреждения, метаданные и результат сверки. В конце пакета все обработанные работы повторно сверяются с Qdrant.

Для исторических `failed`, `text_fallback` и `stale` предусмотрены отдельные переключатели `-RetryFailed`, `-RetryFallback` и `-RetryStale`. Без соответствующего переключателя работа откладывается. Происхождение ранее индексированной записи, которое нельзя подтвердить, также остаётся отложенным для ручной проверки. Поиск и повторное индексирование запускаются только для ID манифеста. Штатная команда `ai:index-artwork` использует `force=true` и может выполнять отдельную попытку даже после лимита автоматической сверки. Счётчики и статусы не сбрасываются.

Если после остановки в журнале есть `dispatch_intent` без `result`, продолжение проверяет актуальную запись и очередь. При подтверждённом Vision и совпадении точки записывается восстановленный результат. В остальных случаях инструмент останавливается для проверки. Если очередь содержит отложенное, зарезервированное или ожидающее задание, требуется сначала выяснить его состояние. При исключении анализа, ошибке индексации, fallback, несовпадении ревизии или недоступности проверки инструмент завершает текущий запуск. Состояние сервиса при ошибке проверяется отдельно. Событие `service_unavailable` фиксирует недоступность Ollama, расхождение моделей или общую неготовность AI-сервиса. Для разграничения этих случаев сохранён тип ошибки проверки.

Журнал `events.jsonl` содержит `batch_started`, `dispatch_intent`, `result` и `batch_verified`. При недоступной инспекции результат отмечается `inspection_unavailable`. Файл блокировки на уровне проекта защищает от одновременных запусков этой обёртки на данном компьютере. Он не управляет другими способами запуска worker, поэтому при работе с проектом необходим исключительный доступ к AI-очереди.

## Продолжение и сверка

Новая версия хранит контрольные точки по ID в `events-v2.jsonl`. Журнал привязан к SHA-256 неизменяемого манифеста, проекту, базе и её UUID, коллекции, экземплярам Redis/Qdrant, очереди и версиям схемы и промпта. Обычное продолжение читает контрольные точки локально и проверяет только новые ID, явно выбранные группы повторов и незавершённые задания. После обработки последнего доступного пакета инструмент в отдельном проходе сверяет весь манифест с MySQL и Qdrant. `-VerifyAll` принудительно проверяет актуальное состояние всех ID, включая ранее отложенные. `-VerifyAll -DryRun` также оставляет журнал без изменений.

Намерение отправки записывается на диск до запуска Artisan. При возобновлении инструмент отделяет оборванную строку журнала и проверяет незавершённую отправку. Для восстановления результата нужны пустая очередь, более свежая завершённая попытка и совпадение её ревизии с намерением и текущей записью. При отсутствии доказательства инструмент останавливается с `dispatch_unresolved`. Если проверка результата недоступна, событие `result_unavailable` оставляет намерение открытым. До возобновления нужно сверить очередь, журнал попыток и ревизию работы. Если подтверждено, что отправки и попытки не было, можно начать новый журнал по тому же манифесту: первые проверки используют актуальный MySQL и Qdrant.

`batch_verified` записывается после успешной сверки **каждого** ID пакета. Расхождение или ошибку проверки фиксирует `batch_verification_failed`. При следующем запуске результаты такого пакета, которые ещё не прошли итоговую сверку, проверяются повторно без автоматической повторной отправки. Итоговые счётчики образуют непересекающиеся группы: `completed`, `remaining`, `failed`, `fallback`, `deferred`, `ineligible`. `remaining` включает новые задачи и ID, до которых дошёл только локальный план. Исторический подтверждённый fallback учитывается в `fallback`, даже если текущий статус MySQL — `failed`. Флаг `complete` требует сверки всего манифеста и успеха всех его записей. `reconciled_at` показывает время последнего полного прохода. Повторный быстрый запуск может вернуть его сохранённый результат, а `-VerifyAll` проверяет изменения, внесённые после этого времени. `inspected_ids` показывает реально проверенные в данном запуске ID.
