> Это исторический снимок первоначального аудита. После него исправлены ключевые ошибки AI-контура и добавлен импорт `--index`. Актуальные команды и границы проверки находятся в [инструкции векторной индексации](ai-indexing-setup.md).

Дата проверки: **24 октября 2026 года**, часовой пояс пользователя — Asia/Qyzylorda. Проверен рабочий каталог `B:\projects\library-stroll-vue`, включая существующие незакоммиченные изменения.

## 1. Главный вывод

В проекте реализован существенный каркас семантического поиска артов: Laravel вызывает отдельный FastAPI-сервис, тот обращается к Ollama для анализа изображений/текста и вычисления embeddings, а векторы должен хранить Qdrant. Результаты векторного поиска объединяются с SQL-поиском по алгоритму Reciprocal Rank Fusion (RRF).

**Сейчас сквозной семантический поиск не работает как включённая и проверенная функция приложения.** В Laravel установлено `AI_SERVICE_ENABLED=false`; Python API на порту 8001 и Qdrant на 6333 не отвечают. Кроме того, установленный Python-клиент Qdrant несовместим с поисковыми вызовами в коде: `AsyncQdrantClient.search` отсутствует в версии 1.18.0. Простого запуска сервисов и включения флага недостаточно.

**Ollama доступен, необходимые модели установлены, реальные текстовые embeddings успешно получены.** Это подтверждает работоспособность части инфраструктуры, но не всей цепочки поиска.

Реальный structured-анализ текста через клиент проекта не завершился за штатный timeout 180 секунд (`ReadTimeout`). Поэтому успешное получение AI-метаданных от chat-модели в этом окружении не подтверждено. Наличие модели в `/api/tags` не гарантирует приемлемую скорость inference.

Проверка vision через тот же клиент на `public/images/main/gallery/1.jpg` также не завершилась в пределах отдельного диагностического лимита 60 секунд. Это не проверка полного штатного 180-секундного бюджета vision; качество её метаданных не оценено.

**Семантического поиска коллекций пока нет.** Нет отдельного индекса, AI-метаданных, задач обработки, Python API и вкладки результатов для коллекций. Не реализован и векторный поиск артов с ограничением по конкретной коллекции.

Проект подходит как основа дальнейшей реализации. Сначала следует исправить блокирующие ошибки AI-контура, подтвердить сквозной сценарий на одном арте, затем добавить коллекции и измерить качество поиска.

- `User` имеет работы и коллекции; роли и права реализованы через Spatie Permission.

- Работа может одновременно входить в несколько коллекций.
- `Collection` содержит `user_id`, `name`, `is_private`; описания и AI-полей в модели нет.
- Лайки, комментарии, жалобы, диалоги и сообщения обеспечивают социальные функции.
- `ArtworkAiMetadata` связан с работой один к одному; `AiProcessingRun` хранит историю AI-операций.

Значение `artworks.has_ai` задаёт пользователь: оно означает, что сама работа создана с помощью ИИ. Оно не означает наличие embedding, готовность индекса или успешность анализа.

## 5. Роли моделей и смысл векторов

| Модель | Как используется | Что делает |
| --- | --- | --- |
| `qwen3:8b` | `OllamaClient.analyze_text()` → `/api/chat` | Выделяет метаданные из названия, описания и тегов, если изображения нет |
| `qwen3-vl:4b` | `analyze_image()` → `/api/chat`, изображение в Base64 | Описывает изображение с учётом текстового контекста |
| `qwen3-embedding:0.6b` | `embed()` → `/api/embed` | Преобразует текст арта и пользовательский запрос в сопоставимые векторы |

Ollama — сервер исполнения моделей. Поисковая близость считается по embeddings. Chat/vision-модель обогащает описание при индексации; на каждый поисковый запрос chat-модель сейчас не вызывается.

В Qdrant предусмотрен один плотный текстовый вектор на точку, расстояние `COSINE`. Размерность определяется реальным пробным embedding при запуске AI-сервиса, а не жёстко заданным числом 1024. Проверка совместимости с существующей коллекцией сравнивает размерность.

Изображение непосредственно векторизующей модели не передаётся. Используется цепочка **изображение → текстовое описание/теги vision-модели → текстовый embedding**. Поэтому функция похожих артов ищет близость описаний и смыслов. Поиск по загружаемой пользователем картинке, прямые визуальные embeddings, OCR-пайплайн, аудиоанализ и анализ последовательности видеокадров отсутствуют.

## 6. Индексация арта: полный путь

### 6.1. Публикация

В `StudioController::publish()` проверяются права, наличие медиа и непустого названия, устанавливаются `is_published` и `published_at`. При включённых `ai.enabled` и `auto_analyze_on_publish` создаётся/обновляется запись AI-метаданных со статусом `pending`, затем отправляется `AnalyzeAndIndexArtworkJob`.

Задание направляется в очередь `ai` и помечено `afterCommit`. При фактическом `QUEUE_CONNECTION=database` публикация не ждёт вычисления модели. При выборе `sync` это свойство теряется: job исполняется в процессе запроса.

### 6.2. Обработка

`AnalyzeAndIndexArtworkJob`:

1. Читает работу без глобальных scope; пропускает отсутствующую или неопубликованную.
2. Проверяет UUID ожидаемого медиа, если он передан.
3. Ставит `processing`, увеличивает `attempts`.
4. Берёт `thumb`; для изображения при отсутствии миниатюры пытается взять оригинал.
5. Передаёт название, описание, пользовательские теги и, по возможности, изображение Python-сервису.
6. Получает AI-метаданные.
7. Собирает `searchable_text`: **название + описание + AI summary + AI tags_en + AI tags_ru**.
8. Вызывает индексацию: Python получает embedding и выполняет upsert в Qdrant.
9. Сохраняет метаданные и статус `indexed`, затем пишет историю операции.

Пользовательские теги участвуют в prompt и payload, но явно не добавляются в `searchable_text`. Поля `objects`, `themes`, `styles`, `mood`, `colors` также напрямую в embedding-текст не включаются: их влияние зависит от того, отразила ли модель эти признаки в summary и AI-тегах. Аргумент `metadata` принимается Python-индексатором, но в его текущей реализации не используется для построения вектора или расширенного payload.

### 6.3. Формат метаданных

Сохраняются summary, объекты, темы, стили, настроение, цвета, русские/английские теги, confidence, названия моделей, версии prompt/schema и временные отметки. Pydantic проверяет типы и диапазон confidence `0..1`, а списки очищаются от дублей и ограничиваются 15 элементами.

Prompt запрашивает все обязательные поля и структурированный JSON через `format`. При ошибке разбора JSON предусмотрена одна дополнительная попытка; HTTP-ошибки и таймауты этим циклом не повторяются. При переданном изображении автоматического перехода с vision на text после ошибки нет.

`confidence` — самооценка модели, а не доказанная вероятность правильности. AI-теги отдельно от пользовательских тегов — это разумная граница ответственности.

### 6.4. Что хранится в Qdrant

Имя технической коллекции по умолчанию — `librarystroll_artworks`. Она не является пользовательской коллекцией `App\Models\Collection`: это контейнер векторной БД для всех артов.

Payload содержит ID арта и автора, флаги публикации/приватности/блокировки, тип медиа, `has_ai`, пользовательские теги, content hash и версии схемы/prompt. Полных описаний AI-полей и ID пользовательских коллекций в нём сейчас нет.

Векторы хранятся в Qdrant; MySQL хранит состояние обработки и ссылку `qdrant_point_id`. `embedding_dimension` в PHP-job явно устанавливается в `null`, хотя реальная размерность доступна Python-сервису.

## 7. Как устроены поиски

### 7.1. Основной поиск `/search`

Непустой запрос передаётся `HybridSearchService`:

1. SQL выбирает публично видимые работы по `title LIKE '%query%'`, сортирует по числу лайков и ограничивает список, по умолчанию 50 кандидатами.
2. При включённом AI Python получает текст запроса, строит embedding и должен выбрать ближайшие точки Qdrant, по умолчанию 50.
3. RRF объединяет позиции из двух списков.
4. Laravel повторно загружает работы по ID и применяет актуальную видимость и фильтры.
5. Результат сортируется в порядке RRF и обрезается для страницы.

Формула: `RRF(d) = Σ 1 / (k + rank(d))`, по умолчанию `k=60`. Работа, найденная обеими ветками, получает вклад от каждой. В RRF используются позиции результатов; исходный cosine score в итоговую формулу не подставляется.

Это гибрид **SQL LIKE + dense vector + RRF**. Реализации BM25, sparse-векторов, Elasticsearch или полнотекстового индекса в текущем контуре не обнаружено. LIKE ищет название арта; описание и теги не являются самостоятельными полями этой lexical-ветки.

При выключенном AI, исключении или пустом semantic-ответе остаётся lexical-ветка. Такой fallback полезен, но скрывает техническую неработоспособность AI от обычного посетителя: поиск может открываться и выдавать результаты без единого векторного совпадения.

### 7.2. Фильтры и пределы

Сервис поддерживает тип, тег, `has_ai`, автора; `SearchController` фактически передаёт только тип и тег. Аргумент `$filters` в `semanticSearch()` не передаётся дальше в AI-клиент. Поэтому Qdrant выбирает общие top-N, а фильтрация Laravel может удалить большинство кандидатов. Релевантные отфильтрованные работы за пределами top-N не попадут в выдачу.

Контроллер запрашивает `page: 1, perPage: 60` и не передаёт страницу из запроса. Сервис обрезает RRF до `$perPage * 3`, а `AI_SEARCH_FINAL_LIMIT` фактически не используется. Значение `total` описывает только оставшиеся кандидаты, а не полное число совпадений в каталоге.

### 7.3. Автодополнение и другие разделы

`/search/suggestions` выполняет обычный SQL LIKE по названиям работ, тегам и авторам. Поиск в студии и менеджере коллекций также lexical. Галерея использует обычную фильтрацию и сортировку. Векторный поиск не подключён автоматически ко всем этим экранам.

В поисковом интерфейсе есть вкладки «Работы», «Теги», «Авторы». Список `collections` в props используется для добавления артов в свои коллекции; это не результаты поиска коллекций. Значение `type` в модальном поиске означает категорию сущности (`artwork`, `tag`, `author`), а в фильтрах hybrid-сервиса — тип медиа (`image`, `video`); семантику параметров следует развести.

### 7.4. Похожие работы

`/artworks/{id}/similar` проверяет доступ к исходному арту. Если AI включён и его метаданные `indexed`, вызывается Python `/similar`; иначе применяется подбор по общим тегам с сортировкой по лайкам. Возвращённые Python ID снова проверяются Laravel.

В semantic-ветке параметр `$page` не используется: всегда берутся первые `$perPage` элементов одного набора. `hasMore` вычисляется до окончательного удаления недоступных кандидатов. Поэтому при исправном Qdrant возможны повторения на следующей странице и неверный признак продолжения.

`StudioController::searchCollections()` выбирает только свои коллекции и ищет `name LIKE '%query%'`. `CollectionController` обеспечивает CRUD и просмотр с проверкой приватности, но не вызывает AI. Связь `artwork_collection` не запускает пересчёт какого-либо семантического представления коллекции.

## 9. Подтверждённые дефекты и риски

Приоритет **P1** означает необходимость исправления до включения функции для пользователей; **P2** — нарушение актуальности, полноты, качества или эксплуатационной устойчивости. Для каждой проблемы указан способ подтверждения; предположения о последствиях отделены от воспроизведённых ошибок.

### P1-01. Поисковые вызовы несовместимы с установленным Qdrant SDK

Источник: `ai-service/app/clients/qdrant.py`, строки 114 и 159. В обоих методах вызывается `self._client.search(...)`.

В `.venv` установлен `qdrant-client 1.18.0`; `hasattr(AsyncQdrantClient, 'search')` возвращает `False`, `query_points` существует. На настоящем in-memory клиенте вызовы обёртки `search()` и `similar()` воспроизвели `AttributeError`.

Исправление: перейти на поддерживаемый `query_points`, передавать вектор через соответствующий аргумент API, разбирать `QueryResponse.points`; закрепить и проверять совместимые версии Python-клиента и Qdrant server. Понижение версии SDK без теста совместимости — временный обход, а не проверенное решение.

### P1-02. Для похожих артов исходный вектор не запрашивается

Источник: `qdrant.py`, строки 139–149. `scroll()` вызывается без `with_vectors=True`, после чего читается `points[0].vector`.

У установленного клиента default — `with_vectors=False`. На in-memory базе с реально записанным вектором `scroll()` вернул `vector=None`. Даже после перехода на новый поисковый API этому пути потребуется явное получение вектора либо запрос соседей по ID точки.

### P1-03. Переиндексация после редактирования никогда не вызывается

Источник: `app/Actions/Artwork/UpdateArtwork.php`, строки 17 и 53. Метод возвращает результат `DB::transaction(...)`, а `maybeDispatchReindex(...)` расположен после этого `return`.

Следствие: изменения названия, описания и тегов сохраняются в MySQL, но существующий вектор остаётся прежним. Исправление: получить результат транзакции в переменную и выполнить отправку задания до возврата результата с корректной привязкой к commit.

### P1-04. Удаление индекса ошибочно журналирует уже удалённый artwork_id

Источники: `DeleteArtwork::handle()`, `DeleteArtworkIndexJob::handle()`, миграция `create_ai_processing_runs_table`.

Работа сначала удаляется из MySQL, затем отправляется задача удаления точки. После успешного HTTP DELETE задача пытается вставить `AiProcessingRun` с ID отсутствующей работы. Foreign key запрещает новую запись. `nullOnDelete()` обнуляет ссылки уже существующих записей, но не разрешает новые несуществующие ID.

В изолированной SQLite с настоящими миграциями и HTTP fake воспроизведена ошибка `FOREIGN KEY constraint failed`. Путь catch пытается вставить такую же недопустимую ссылку и тоже падает. При этом точка во внешнем хранилище уже могла быть удалена.

Исправление: журналировать операцию с `artwork_id=null`, а исходный ID сохранять в `parameters`, либо использовать отдельную схему журнала удаления.

### P1-05. Длительность AI-операций вычисляется со знаком минус

Источники: `AnalyzeAndIndexArtworkJob::recordRun()` и `DeleteArtworkIndexJob`. Используется `now()->diffInMilliseconds($startedAt)`.

В установленном Carbon для времени начала на секунду раньше получено **-1000**. Столбец `latency_ms` объявлен `unsignedInteger`. SQLite в тестах принимает отрицательные значения; MySQL в strict-режиме может отклонить такую вставку. На рабочей MySQL ошибочная запись намеренно не создавалась: подтверждены знак выражения и несовместимая схема.

В результате успешная внешняя индексация может быть ошибочно переведена в `failed` при записи истории. Исправление: считать интервал от начала до конца с неотрицательным результатом, проверить именно на MySQL и изолировать ошибку телеметрии от результата бизнес-операции.

### P1-06. Интервалы очереди допускают повторную выдачу выполняющегося задания

В job установлен `timeout=300`, а в database queue `retry_after=240`. Если обработка длится более 240 секунд, другой worker может получить то же зарезервированное задание до окончания первого. Уникальность dispatch не заменяет корректное резервирование очереди.

Дополнительно анализ и индексация — разные HTTP-запросы с таймаутом 180 секунд каждый; повторы index и JSON-разбора могут увеличить общее время за пределы 300 секунд. Исправление: согласовать бюджеты времени, выделить короткий timeout поиска, увеличить `retry_after` выше максимального времени исполнения с запасом либо разбить стадии обработки. В Windows также проверить реальное поведение timeout worker: расширение `pcntl` в проверенном CLI отсутствует.

### P2-01. Хеш не описывает все входные данные и не защищает от устаревшей задачи

Хеш включает только title, description и UUID медиа. Изменение тегов без изменения текста даёт прежний хеш и было бы пропущено даже после устранения недостижимого кода. Флаги приватности, блокировки и `has_ai`, версии prompt/schema/модели также не входят в него.

Задание принимает `expectedContentHash`, но не сравнивает его с актуальным содержимым перед записью результата. Разные хеши дают разные unique ID; несколько задач для одной работы могут выполняться параллельно и перезаписывать более новый результат. Проверка UUID защищает только от части сценариев замены медиа и выполняется до длительного запроса модели.

Нужно каноническое представление всех влияющих полей, версия ревизии, блокировка/контроль актуальности до и после внешних операций. Изменение privacy/payload желательно обрабатывать отдельно от дорогостоящего повторного vision-анализа.

### P2-02. Первая индексация не гарантирует идемпотентность

Если point ID ещё не сохранён в MySQL, Python создаёт `uuid4()`. Если upsert завершился, а ответ потерялся, повтор с пустым `idempotency_key` создаст новую точку. Это особенно существенно при включённых HTTP retries.

Нужен детерминированный point ID по типу сущности и её ID либо заранее сохранённый UUID. Удаление всех точек по `artwork_id` уменьшает последствия дублей, но не предотвращает их. RRF также не устраняет дополнительный вклад повторяющегося ID внутри одного списка.

### P2-03. Сверка индекса неполна

`AiReconcileCommand` обрабатывает `stale`, `failed` с `attempts<5`, старые `pending` и опубликованные работы без metadata. Но `$staleHours` читается и не используется; зависшие `processing` не восстанавливаются; существование точек в Qdrant не проверяется; осиротевшие точки не удаляются.

Потеря Qdrant storage при сохранённых статусах `indexed` может остаться незамеченной. После пяти попыток `failed` перестаёт автоматически подбираться. Нужно определить восстановление, dead-letter-процесс и сверку MySQL ↔ Qdrant.

`ai:index-artwork` сообщает, что неопубликованная работа будет обработана как ручной запрос, но job пропускает её; metadata может остаться `pending`. Сообщение и фактическое поведение следует согласовать.

### P2-04. Фильтры применяются после ограниченного semantic top-N

Причина и последствия описаны в разделе 7.2. Нужны allowlist/mapping фильтров в Qdrant и повторная проверка Laravel. Поля `type` и `author_id` должны преобразовываться в payload-имена `media_type` и `user_id`; простая пересылка исходного массива недостаточна.

### P2-05. Пагинация не соответствует выбранным кандидатам

Semantic similar игнорирует номер страницы. Основной SearchController всегда запрашивает первую страницу. Лимиты и `total` относятся к усечённому пулу. Нужна стабильная пагинация с явным ограничением или курсором, а также вычисление `hasMore` после фильтрации.

### P2-06. Модель и готовность коллекции контролируются недостаточно

`ensure_collection()` выполняется только при старте FastAPI. Ошибка ловится и превращается в warning; процесс продолжает запуск. Если зависимость восстановится позже, автоматическое создание коллекции перед index не гарантировано.

`/health` проверяет доступность `/api/tags` и списка коллекций Qdrant, но не наличие нужных моделей, фактический embedding, существование целевой коллекции и совместимость её векторов. Поэтому даже `status=ok` недостаточно для готовности поиска. Замена embedding-модели на другую той же размерности тоже требует переиндексации: одинаковый размер не означает одинаковое векторное пространство.

### P2-07. Поток обновления доступа и удаления данных неполон

Публичная выдача повторно фильтруется MySQL — это действующая защита. Но job выбирает опубликованные работы без global scopes и не исключает private/blocked перед отправкой в AI. Автоматическая синхронизация payload при смене видимости или блокировке не реализована; удаление пользователя через каскад БД обходит `DeleteArtwork`.

При анализе приватных работ нужна явная политика, а при их попадании в общий индекс — фильтры доступа на обеих границах. Внешний Python API не должен быть доступен посетителям как самостоятельный поиск: он возвращает сырые ID и не выполняет авторизацию Laravel.

### P2-08. Переранжирование — только заглушка

Endpoint `/api/v1/rerank` в обеих ветках возвращает исходный порядок и `reranked=false`, не использует модель и не соблюдает `limit`. В Python Settings нет `rerank_enabled`; PHP-флаг не используется гибридным поиском для вызова rerank. Документировать эту возможность как готовую нельзя.

### P2-09. Качество vision-данных ограничено миниатюрой

Job предпочитает изображение шириной 300 px. У видео используется один thumbnail; при его отсутствии возможен только текстовый анализ. Отдельный MP4 preview — не вход модели. Нет последовательности кадров, анализа движения или аудио. Для мелких объектов, текста и сложной композиции миниатюры может быть недостаточно; это требует проверки на датасете.

### P2-10. Тесты обходят проблемные границы интеграции

Python-тесты подменяют Ollama и Qdrant целиком через `AsyncMock`; PHP-поиск подменяет AI-клиент, а клиентские тесты используют `Http::fake`. Поэтому зелёный набор не проверяет реальный SDK, передачу изображений, prompt, миграции MySQL и исполнение job с внешними сервисами. Тест объединения hybrid-выдачи проверяет HTTP 200, но не весь ожидаемый состав и порядок результатов.

### Дополнительные эксплуатационные замечания

- API key проверяется только если он задан; оставить API на loopback разумно, а при сетевом развёртывании нужна согласованная защита Laravel → Python.
- Файловый endpoint читает upload целиком и не ограничивает в коде MIME/размер; error detail возвращает текст исключения. Нужны ограничения на доверенной границе сервиса.
- `request_id` генерируется в PHP, но не передаётся заголовком в Python; сквозная корреляция логов не реализована.
- Нет кэширования query embeddings, ограничения параллелизма inference, отдельной политики перегрузки и метрик semantic fallback.
- Повторная загрузка likes/collections и вычисляемые свойства моделей могут создавать N+1 SQL-запросы. Это следует измерять на реальном запросе и пользователе.
- `composer dev` запускает очередь по умолчанию, но не отдельный worker `ai`, а также не запускает FastAPI/Qdrant/Ollama. Одной этой команды для AI недостаточно.
- Composer в контексте проверки сообщил о недоступной временной директории PHP 8.2; это отдельная настройка окружения, не причина найденных ошибок поиска.

В текущем chat payload не задаются явный бюджет генерации и управление thinking. Увеличивать таймауты без измерений недостаточно: это также увеличит ожидание и нагрузку очереди.

## 11. Что нужно сделать для семантического поиска коллекций

### 11.1. Два отдельных сценария

**Найти саму коллекцию по смыслу.** Например, «уютные акварельные коты» должны находить коллекцию «Тихие вечера», если её содержимое соответствует запросу.

**Найти арт внутри коллекции.** Например, поиск «кошка у окна» ограничивается выбранной коллекцией и актуальными правами пользователя.

Это разные запросы, которым нужны разные результаты и правила доступа. Существующий UI выбора коллекции не реализует ни один из них семантически.

### 11.2. Предлагаемый первый вариант

Сначала использовать уже вычисленные embeddings артов: искать работы и группировать результаты по доступным пользовательским коллекциям. Для ранжирования коллекций учитывать несколько лучших совпадений с ограничением вклада больших коллекций. Это даёт первый рабочий сценарий без повторного vision-анализа каждой коллекции.

Затем добавить отдельный индекс коллекций: название, при необходимости новое пользовательское описание и агрегированное описание доступных артов. Вычислять summary и embedding коллекции при переименовании, изменении состава и изменении AI-метаданных её работ. Для больших коллекций агрегировать порциями, а не передавать модели весь каталог.

| Уровень | Требуемое расширение |
| --- | --- |
| MySQL | Метаданные индекса коллекции, ревизия состава, point ID, статусы, модели и версии |
| Laravel | Контракт/DTO, задания index/delete, обработка attach/detach, rename, privacy и удаления |
| Python | API индексации/поиска коллекций, строгие схемы и allowlist payload |
| Qdrant | Отдельная техническая коллекция либо явно типизированные точки; детерминированные ID |
| Поиск артов внутри коллекции | Проверка доступа к коллекции и membership; фильтр кандидатов с последующей SQL-проверкой |
| Vue | Вкладка «Коллекции», область поиска, корректная пагинация и состояние недоступного AI |
| Тесты | Изменение состава, приватность, скрытые/удалённые арты, устаревшие задания, ранжирование |

При обновлении payload нужно учитывать несколько коллекций на один арт и независимую приватность арта/коллекции. Публичный summary коллекции не должен включать закрытые работы, даже если владелец их видит. Для личного поиска потребуется отдельная авторизованная область, а не ослабление публичного `publiclyVisible()`.

Это предложение дальнейшей реализации; перечисленные расширения в рамках аудита не внедрены.

## 12. Рекомендуемый порядок доведения до рабочего состояния

1. Исправить P1-01 и P1-02, зафиксировать зависимости и добавить тест реального Qdrant-клиента.
2. Исправить недостижимую переиндексацию, журнал удаления и знак latency; проверить на MySQL.
3. Согласовать timeout/retry_after, повторные попытки и отдельную AI-очередь; реализовать стабильный point ID и контроль ревизии.
4. Запустить Qdrant с постоянным storage и FastAPI, проверить модели и целевую векторную коллекцию.
5. Выполнить один сквозной сценарий с отдельной тестовой работой: анализ → индекс → смысловой запрос → похожие → изменение → повторный поиск → удаление.
6. Применить фильтры и исправить пагинацию; добавить наблюдаемость fallback и processing-ошибок.
7. Подготовить размеченный набор запросов, измерить baseline SQL, vector и hybrid.
8. Добавить поиск внутри коллекций и затем ранжирование самих коллекций.
9. После этого включать массовую индексацию и пользовательскую функцию.

### 12.1. Команды для будущего запуска после исправлений

Ниже инструкция к последующему развёртыванию; её наличие не означает, что сервисы уже запущены аудитом. Если `php -v` всё ещё показывает 8.1, использовать полный путь PHP 8.2 или обновить окружение терминала.

```powershell
Set-Location B:\projects\library-stroll-vue
$env:Path = 'C:\OSPanel\modules\PHP-8.2;' + $env:Path
php -v
php artisan migrate:status
```

Модели уже установлены. Если их потребуется восстановить:

```powershell
ollama pull qwen3:8b
ollama pull qwen3-vl:4b
ollama pull qwen3-embedding:0.6b
```

Для Qdrant сначала проверить Docker Desktop и существующие контейнеры, чтобы не создавать дубликат. В команде создания нового экземпляра следует фиксировать протестированный server image tag и постоянный volume. Пример формы команды:

```powershell
docker ps -a
# Заменить <tested-tag> на выбранную и проверенную версию перед запуском.
docker run -d --name librarystroll-qdrant `
  -p 127.0.0.1:6333:6333 `
  -v librarystroll-qdrant-data:/qdrant/storage `
  qdrant/qdrant:<tested-tag>
```

Python нужно запускать из `ai-service`, поскольку `.env` читается относительно текущего каталога:

```powershell
Set-Location B:\projects\library-stroll-vue\ai-service
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8001
```

В Laravel после исправлений задать `AI_SERVICE_ENABLED=true`, `AI_SERVICE_URL=http://127.0.0.1:8001`, `AI_PROCESSING_QUEUE=ai` и согласовать API key с Python. После изменения `.env` учесть config cache и перезапустить долгоживущие workers. Для job с timeout 300 разумный исходный `DB_QUEUE_RETRY_AFTER` должен быть больше 300, например 420, **если** общий бюджет обработчика действительно укладывается в 300 секунд; сами таймауты HTTP тоже необходимо согласовать.

```powershell
Set-Location B:\projects\library-stroll-vue
php artisan config:clear
php artisan ai:health
php artisan queue:work --queue=ai --timeout=300
```

Отдельно нужны worker основной очереди для медиа и scheduler для reconcile. Планировщик проекта настроен на `ai:reconcile --limit=25` каждые 30 минут при включённом AI. `ai:health` при выключенном флаге возвращает success с сообщением «disabled» — exit code 0 без чтения вывода не доказывает работоспособность.

Для одного тестового опубликованного арта: `php artisan ai:index-artwork <id>`. Массовый `ai:reindex-all` запускать после проверки одного полного цикла; он ставит задания в очередь, а не ждёт готовности индекса. Сидеры публикуют работы напрямую через Eloquent и не заменяют явную AI-индексацию существующего каталога.

## 13. Как измерить качество

Документ `docs/ai/evaluation-plan.md` задаёт полезную основу: Precision@5/10, Recall@10, MRR, nDCG@10, p50/p95 задержки. Но `ai:evaluate` отсутствует, готового golden dataset не найдено, численные показатели качества каталога пока не измерены.

Начать можно с 30–50 вручную размеченных запросов и расширять набор после первых ошибок. Нужны русские, английские и смешанные формулировки: объекты, стиль, настроение, композиция, сочетания признаков, синонимы, запросы без релевантных работ. Для коллекций оценивать отдельно релевантность самой подборки и поиск внутри неё.

Сравнить на одинаковом снимке данных SQL baseline, dense vector, hybrid RRF, hybrid с vision-метаданными. Измерять холодные и прогретые модели отдельно, фиксировать версии и параметры, показывать долю fallback и ошибки. Приватные, заблокированные, удалённые работы и авторы должны быть отдельными проверками доступа, а не просто отрицательными примерами релевантности.

Критерий готовности: сквозной сценарий стабильно проходит с реальными сервисами, индекс обновляется и очищается без дублей, скрытый контент не появляется в публичной выдаче, страницы не повторяются, а улучшение релевантности подтверждено сравнением с SQL на размеченном наборе. Целевые значения задержки нужно выбрать по результатам измерений на доступном оборудовании.

### Официальные источники, использованные для проверки API
