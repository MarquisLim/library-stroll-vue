# Этап 5.4-1C. Лексический и гибридный поиск

На независимых формулировках экспериментальный Hybrid поднял Recall@20 по известным полным совпадениям с 0,690 до 0,747 и вывел пять новых пар «запрос — работа», отсутствовавших у обеих базовых стратегий в первых 50 позициях. Русский nDCG@5 снизился с 0,344 до 0,333, а задержка retrieval p50 выросла с 95 до 362 мс. Разметку выполнял один ИИ-рецензент по изображениям. Результат предварительный, `AI_ASSISTANT_LEXICAL_METADATA_ENABLED` выключен по умолчанию.

## Исходная реализация

Исходный код взят из `docker`, коммит `5a22a66c8ddc94e0f5bf419da76dc3bdab811020`. В штатной стратегии `HybridSearchService` использовал `title LIKE "%запрос%"` и упорядочивал результаты по числу лайков. Добавление вводной фразы, знака препинания или другого порядка слов обычно ломает вхождение. Названия на другом языке и совпадения из описаний, объектов или тегов оставались за пределами этой ветки. `AssistantQueryNormalizer` при опциональном включении мог изменить используемый запрос в прямом поиске, но поиск по целой фразе в заголовке сохранялся. RRF принимал до 50 лексических и 50 Dense-кандидатов, `k=60`, объединённый лимит 100. Штатный вход ассистента берёт 20 позиций Hybrid перед дополнительной проверкой доступности. RAG выбирает до пяти источников.

MySQL на стенде — 8.4.13, сопоставление `utf8mb4_0900_ai_ci`, `innodb_ft_min_token_size=3`. На таблицах работ и AI-метаданных есть B-tree индексы, включая ключ связи AI-метаданных с работой. `EXPLAIN` для `LIKE '%Тарелка.%'` показывает `ALL` по работам с оценкой в 512 строк, временной таблицей и сортировкой. Ведущий `%` мешает индексу обслужить условие как диапазон. [Снимок MySQL и EXPLAIN](../../storage/app/ai-stage-05-04/5.4-1c/mysql-audit.json).

InnoDB FULLTEXT применим к текстовым колонкам `CHAR`, `VARCHAR`, `TEXT`. Для одновременного поиска по таблице работ, связанным AI-метаданным и JSON-массивам понадобилась бы текстовая проекция с поддержкой обновлений и согласованием токенизации и стоп-слов. SQL-поиск по отдельным токенам через `LIKE '%…%'` размножил бы условия сканирования и оставил проблему границ термов. Для эксперимента на 511 работах выбрано ограниченное пакетное чтение с оценкой в Laravel. Миграций, нового поискового сервера и обновлений индексов нет. [MySQL 8.4 Column Indexes](https://dev.mysql.com/doc/refman/8.4/en/column-indexes.html) · [MySQL 8.4 Natural Language Full-Text Searches](https://dev.mysql.com/doc/refman/8.4/en/fulltext-natural-language.html).

## Экспериментальная стратегия

- Доступные поля и веса — заголовок 7, Objects 6, Tags RU и EN по 5, Vision Summary 3,5, Styles 2,5, Themes 2, описание 1,5 и Colors 0,35. Используются AI-поля с актуальными `content_hash` и UUID медиа, статусом `indexed` и указанной Vision-моделью. Заголовок и описание доступны и без актуальных AI-полей.
- Нормализация приводит Unicode-текст к нижнему регистру, унифицирует «ё» и «е», делит по пунктуации и пробелам и убирает часть служебных слов и вводных конструкций RU/EN. Совпадение целого токена имеет множитель 1, простой словоформы — 0,65. Похожие словоформы определяются ограниченным набором окончаний. Перевод запроса, словарь синонимов и подстрочные совпадения отсутствуют. Совпадение последовательности нормализованных термов даёт бонус в текстовом поле.
- Вес редкого терма выше. Для каждого терма берётся лучшее совпадение с ограниченным бонусом от подтверждения в других полях. Сумма весов умножается на квадрат доли найденных термов. Бонус за фразу добавляется отдельно. При равной оценке выше работа с меньшим ID. Палитра даёт слабый сигнал о присутствии оттенка и сама по себе не добавляет многословное совпадение. Положение оттенка на изображении и визуальные отношения этот алгоритм не устанавливает.
- За запрос читается не более 1 001 работы для проверки порога в 1 000. Термы ограничены двенадцатью, вес рассчитывается по первым 2 048 байтам каждого поля и первым 15 элементам списка. Работы, медиа, теги и AI-метаданные читаются четырьмя SQL-запросами. Перед отсечением списка до 50 позиций используется существующая пакетная проверка прав, AI-индексации, MIME и наличия файла. Проверка после Hybrid сохранена. Экспериментальная ветка не загружает лайки и коллекции каждой работы. Проверка наличия файлов выполняет до одной операции хранилища на совпавшую работу.
- При превышении порога применяется `title_like` с причиной `corpus_limit`. При исключении экспериментальной ветки применяется тот же поиск с причиной `metadata_lexical_unavailable`. Сбой Dense позволяет использовать доступный лексический список по действующему поведению Hybrid. Обычный поиск по каталогу продолжает вызывать прежнюю стратегию. Экспериментальный флаг относится к новому поиску ассистента. Intent Router, Query Understanding, Context Resolver, RAG и ColBERT сохранили свои настройки и контракты. [Лексический поиск](../../app/Services/Search/MetadataLexicalSearch.php) · [Hybrid](../../app/Services/Search/HybridSearchService.php) · [Вход ассистента](../../app/Services/Search/AssistantArtworkSearch.php).

Диагностика и JSON-экспорт сохраняют исходную и использованную фразу, очищенные термы, запрошенную и применённую стратегии, поля с типами совпадений, оценки и ранги Lexical, Dense и RRF, признак кандидата только из Lexical, причины исключений и fallback. Отдельно измеряются чтение лексического корпуса, оценки и проверка доступности. Для недоступных картин сохраняется только суммарное число лексических исключений. Прежняя проверка актуального доступа к кандидатам, редактирование чувствительного текста и административный доступ к диагностике действуют и для новых полей. Прежние диагностические снимки поддерживаются без миграции. [Диагностика](../../app/Services/Search/AssistantSearchDiagnostics.php) · [Интерфейс](../../resources/js/Components/Assistant/AssistantSearchTrace.vue).

Время включает серверный retrieval и подготовку карточек, измеренных до формирования расширенной диагностики. Composer, Vision, ColBERT и обработчики диалога в этом изолированном прогоне не вызывались. По одному прогревочному запросу на стратегию, затем три повтора на запрос с чередованием порядка A–D.

Исходные фразы и Dense-ранги совпали во всех 18 запросах A/B/D, лексические ранги совпали в C/D, все три повтора дали одинаковые ID и порядок. nDCG использует степени релевантности 0/1/2 и коэффициент полезности `2^grade − 1`. В основной таблице Hit, MRR и Recall учитывают только степень 2. Recall усредняется по 16 запросам с известными полными совпадениями, знаменатель задаётся объединённой разметкой. Для запросов без известного совпадения Hit, MRR и nDCG получают 0. Места с неизвестной оценкой дают нулевую измеренную полезность. Определённые оценки покрывают в A/B 172 из 180 позиций @10 и 355 из 900 @50, в C 152 из 160 и 301 из 646, в D 172 из 180 и 453 из 900. Recall отражает обнаружение известных релевантных работ. Доля найденного во всём каталоге остаётся неизвестной.

Лексические совпадения пригодны для генерации кандидатов. Фон, принадлежность цвета, точное количество, пространственные отношения и отрицания требуют независимой проверки доказательств, с явным статусом «недостаточно доказательств». Для решения о штатном включении нужны человеческая перепроверка, более крупная выборка RU/EN и оценка задержки на рабочей нагрузке. Этап 5.4-1D в этих изменениях не реализован.
